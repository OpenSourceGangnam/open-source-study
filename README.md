# RateLimiter, 왜 핵심적인가?

송금 프로젝트와 같이 민감하고 실시간성이 중요한 시스템에서는 **빠른 응답**과 함께 **예측 가능한 안정성**이 동시에 중요합니다.
**RateLimiter**는 단순히 "요청 제한" 도구를 넘어서, 내부 시스템 자원을 보호하고 전체 서비스 품질을 보장하는 하나의 **설계 키워드**로 작동합니다.

---

## 내부 자원 보호의 실질적 의미

* **DB 트래픽 과다 · Connection Pool 고갈**
  RateLimiter는 동시에 처리할 수 있는 요청 수를 제한하여, DB와 같은 핵심 인프라 자원을 보호하는 첫 번째 방어선 역할을 수행합니다.

* **과금되는 외부 API 호출 관리**
  외부 API 사용량을 제한하여, 예기치 않은 비용 폭증과 시스템 불안정성을 방지할 수 있습니다.

* **MSA · 분산환경에서의 자원 분배**
  여러 인스턴스 환경에서도 제한된 리소스를 효율적으로 분배하여, 전체 장애 전파를 차단할 수 있습니다.

**"RateLimiter는 외부 공격보다, 우리 시스템 내부를 지키기 위한 설계다"** 라는 인식을 가져야 합니다.

---

## RateLimiter 사용의 실제적 이점

* 시스템 과부하 및 장애 방지
* 공정한 사용자 자원 분배
* 비용 및 SLA 관리
* 예측 가능한 품질 유지

## 알고리즘별 핵심 특징 및 선택 가이드

| 알고리즘     | 버스트 허용 | 처리율 일정성 | 메모리 효율성 | 실용적 사용처             |
| -------- | ------ | ------- | ------- | ------------------- |
| 슬라이딩 윈도우 | 일부 허용  | 중       | 중\~불리   | 실시간 API, 로그인 제한     |
| 토큰 버킷    | 허용     | 낮음      | 중       | 네트워크, 이벤트 스트림       |
| 리키 버킷    | 불가     | 매우 높음   | 매우 높음   | 네트워크/통신 큐, 방송/패킷 처리 |

* Sliding Window: 시간 경계에 유연, 부드러운 제한

## RateLimiter는 단순한 코드가 아니다

### 실제 운영 환경에서 고려해야 할 요소

* **동시성 및 분산환경 지원**
  Redis, Memcached 등과 연동하여 인스턴스 간 Rate 제한 상태를 공유해야 합니다.

* **최적화 지표 확보**
  멀티스레드, 비동기 처리, 캐싱 전략 등을 통한 공학적 튜닝이 필요합니다.

* **Timeout 및 오류 처리**
  `timeoutDuration` 설정을 통해 실패나 대기 상황에서도 유연하게 대응할 수 있어야 합니다.

## DDD, 아키텍처 설계와의 연결

Resilience4j와 같은 현대 RateLimiter 라이브러리는 다음과 같은 아키텍처 철학을 따릅니다:

* 도메인 로직의 명확한 분리
* 설정(정책)과 실행(알고리즘)의 역할 분리
* 모듈화 및 조합 가능한 구성 (높은 응집도, 낮은 결합도)

이러한 구조는 DDD(Domain-Driven Design) 철학과 맞닿아 있으며,
유지보수성과 재사용성을 극대화할 수 있는 전략적 설계 기반을 제공합니다.

---

## 총정리 – RateLimiter란?

* 내부 자원 보호의 설계 기본 원칙
* 시스템 자가 제어의 출발점
* 품질 보장과 공정한 자원 배분의 핵심 도구

RateLimiter를 도입함으로써 다음과 같은 효과를 기대할 수 있습니다:

* 예측 가능성 향상
* 시스템 신뢰성 확보
* 리스크 관리 체계화
* 장기적으로 확장 가능한 아키텍처 구축 기반 마련

**실제 서비스 운영과 아키텍처 설계에서 RateLimiter는 선택이 아닌 필수입니다.**
