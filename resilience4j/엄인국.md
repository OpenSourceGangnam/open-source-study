# Resilience4j란?

Resilience4j는 Java로 작성된 경량화된 라이브러리로,
MSA 환경에서 주로 사용되는 안정성 패턴을 구현할 수 있도록 도와줍니다.

주요 기능으로는 Circuit Breaker, Rate Limiter, Retry, Bulkhead 등이 있으며,
각 기능을 독립적으로 사용할 수 있어 필요한 부분만 선택적으로 적용할 수 있습니다.

# Reslilience4j에서 제공하는 RateLimiter에 관련해서 공유드립니다.


## RateLimiter 적용 예제

Spring Boot 환경에서 **Resilience4j RateLimiter**를 활용해 요청 제한을 거는 방법을 안내합니다. 아래 예시와 설정을 참고해 `README.md` 파일로 바로 활용할 수 있습니다.

## 1. 의존성 추가

**Gradle**

```groovy
implementation 'io.github.resilience4j:resilience4j-spring-boot2'
implementation 'io.github.resilience4j:resilience4j-ratelimiter'
```

**Maven**

```xml
<dependency>
  <groupId>io.github.resilience4j</groupId>
  <artifactId>resilience4j-spring-boot2</artifactId>
</dependency>
<dependency>
  <groupId>io.github.resilience4j</groupId>
  <artifactId>resilience4j-ratelimiter</artifactId>
</dependency>
```


## 2. RateLimiter 적용 서비스 코드

```java
import io.github.resilience4j.ratelimiter.annotation.RateLimiter;
import org.springframework.stereotype.Service;

@Service
public class MyRateLimitedService {

    // 이 메서드는 RateLimiter가 적용되어 있습니다.
    @RateLimiter(name = "myRateLimitedService", fallbackMethod = "rateLimiterFallback")
    public String processRequest() {
        // 실제 요청 처리 로직
        return "Request processed.";
    }

    // Rate limit 초과 시 호출되는 fallback 메서드
    public String rateLimiterFallback(Throwable t) {
        return "Rate limit exceeded. Please try again later.";
    }
}
```


## 3. 설정 파일 예시 (`application.yml`)

```yaml
resilience4j.ratelimiter:
  instances:
    myRateLimitedService:
      limitForPeriod: 5
      limitRefreshPeriod: 1s
      timeoutDuration: 0
```


## 4. 점검 및 참고 사항

- `@RateLimiter`의 `name` 속성과 설정 파일의 인스턴스명이 반드시 일치해야 합니다.
- 서비스 클래스는 반드시 `@Service` 등으로 Bean 등록되어야 하며, 메서드는 `public`이어야 합니다.
- 내부 메서드 호출 시 RateLimiter가 적용되지 않을 수 있으니, 외부에서 호출해야 적용됩니다.
- 여러 번 연속 호출하여 5회 초과 시 fallback이 정상 동작하는지 확인하세요.


## 5. 자주 발생하는 문제와 해결법

| 문제 상황 | 점검 및 해결 방법 |
| :-- | :-- |
| RateLimiter가 동작하지 않음 | 의존성, 설정, Bean 등록, 이름 일치 여부 확인 |
| fallback 메서드가 호출되지 않음 | fallback 메서드 시그니처(파라미터) 및 접근제어자 확인 |
| 설정값이 적용되지 않음 | 설정 파일 경로 및 YAML 문법 오류 여부 확인 |
| 내부 메서드 호출 시 RateLimiter 미적용 | 외부에서 Bean을 통해 호출해야 AOP 적용됨 |

## 6. 참고

- 설정 및 코드가 정상이어도 캐시나 빌드 문제로 반영이 안 될 수 있으니, 프로젝트 클린/재빌드 후 재시도하세요.
- 문제가 계속된다면, 로그 레벨을 DEBUG로 높여서 Resilience4j 관련 로그를 확인해보세요.

## 7.단점 및 주의점

* 단순히 요청만 제한하므로, 세밀한 트래픽 제어가 필요한 경우에는 추가 구현이 필요할 수 있습니다.

* 분산 환경(멀티 파드, 멀티 인스턴스)에서는 각 인스턴스가 독립적으로 카운트를 관리하므로, 전체 시스템 기준의 일관된 제한을 위해서는 Redis 등 외부 저장소와 연동하는 커스텀 구현이 필요합니다.

* Java 17 이상에서만 2.x 버전을 사용할 수 있습니다

## rateLimiter가 사용하는 토큰 버킷 알고리즘과 고정 윈도우 카운터의 차이점은 무엇인가?

* 토큰 버킷 알고리즘(Token Bucket) 과 고정 윈도우 카운터(Fixed Window Counter) 차이점

|구분 |	토큰 버킷 알고리즘|	고정 윈도우 카운터|
| :-- | :-- | :--|
|동작 방식|	일정 시간마다 버킷에 토큰을 채움. 요청이 오면 토큰을 소모하며, 토큰이 없으면 거부	|일정 시간(윈도우) 동안 허용된 요청 수만큼 카운트. 초과 시 거부|
|버스트 처리|	버킷에 토큰이 남아 있으면 단기간에 많은 요청(버스트) 허용 가능	|윈도우 경계에서 연속된 요청이 몰리면 버스트처럼 허용될 수 있음|
|유연성|	남은 토큰을 다음 주기로 이월 가능(버스트에 유리)	|윈도우가 리셋되면 카운트도 리셋(이월 불가)|
|설정 값|	버킷 용량, 토큰 생성 속도 등	|윈도우 크기, 윈도우당 최대 요청 수 등|
|장점|	- |버스트 트래픽에 유연|	

* 실제 트래픽 패턴에 더 부드럽게 대응

* 사용하지 않은 토큰 이월 가능 | - 구현이 단순

* 메모리 사용량이 적음

* 각 윈도우별 통계 집계 용이 |
* | 단점 | - 상태 관리가 다소 복잡

* 토큰 관리 필요 | - 윈도우 경계에서 트래픽 집중(최대 2배 허용 가능)

* 버스트에 덜 유연 |
* | 예시 | 1초에 5개 토큰 생성, 최대 10개까지 저장. 토큰이 있으면 요청 허용 | 1분에 100건 허용. 1분이 지나면 카운트 리셋 |

### 추가설명

* 토큰 버킷(Token Bucket)

  * 일정 주기로 토큰이 버킷에 쌓이고, 요청이 들어올 때마다 토큰을 소모합니다.

  * 버킷에 토큰이 남아 있으면, 짧은 시간 동안 많은 요청(버스트 트래픽)도 허용할 수 있습니다.

  * 토큰이 없으면 요청이 거부됩니다. 사용하지 않은 토큰은 다음 주기로 이월돼 유연한 트래픽 제어가 가능합니다.

* 고정 윈도우 카운터(Fixed Window Counter)

  * 시간 구간(윈도우)을 나누고, 각 구간마다 요청 횟수를 카운트합니다.

  * 윈도우 내에서 허용된 요청 수를 초과하면 이후 요청은 거부됩니다.

  * 윈도우가 끝나면 카운트가 리셋되므로, 윈도우 경계에서 짧은 시간에 많은 요청이 몰릴 경우 실제로는 설정값의 2배까지 허용될 수 있습니다(버스트 현상)


* 요약하자면...

  * 토큰 버킷은 버스트 트래픽에 유연하고, 사용하지 않은 토큰을 이월할 수 있어 실제 트래픽 패턴에 더 부드럽게 대응합니다.

  * 고정 윈도우 카운터는 구현이 단순하고 메모리 효율적이지만, 윈도우 경계에서 트래픽이 집중될 수 있다는 단점이 있습니다.
